## 一句话

**别再只把 LLM 当代码生成器。** 让它把你的资料编译成一个持续更新、互相链接的 Markdown 知识库——一个长着长着越来越聪明的 wiki。

## 核心洞察：编译器 vs 解释器

Karpathy 用了一个计算机科学的类比点明问题：

- **RAG 像"解释器（Interpreter）"**：每次执行都重新解析一遍源码。
- **我们真正需要的是"编译器（Compiler）"**：先把知识预先编译成可直接执行的结构。

传统做法（上传文件 → 提问时检索片段 → 生成答案）的问题在于**不积累**：你今天问一次"这 5 篇文章共同说明了什么"，模型去找 5 次片段、拼 1 次答案；过两天换个问法，它大概率还要再做一遍。

LLM Wiki 补的就是这层缺口——不是在查询时临时去原始资料里捞，而是**先把资料整理成一层持续存在的 wiki**（摘要页、概念页、实体页、对比页、综合页、索引页），并持续修订。

## 三层架构

| 层级 | 名称 | 作用 | 谁负责 |
|---|---|---|---|
| 第一层 | **Raw sources** 原始素材 | 你策划的源文档：文章、论文、图片、数据文件、代码仓库。**不可变——LLM 只读不改** | 你 |
| 第二层 | **The wiki** 维基 | LLM 生成的 Markdown 目录：摘要、实体页、概念页、对比页、概览、综合。LLM 完全拥有这一层 | LLM |
| 第三层 | **The schema** 说明书 | 一个文档（Claude Code 用 `CLAUDE.md`，Codex 用 `AGENTS.md`），规定 wiki 如何组织、命名约定、摄取/提问/维护的工作流 | 你 + LLM 共同演进 |

**第三层最容易被忽略，但最关键**。没有它，LLM 当然也能整理资料，但每次整理的方式可能都不一样——命名会漂，页面结构会漂，引用习惯也会漂。

Karpathy 的原话：

> Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase.
> （Obsidian 是 IDE，LLM 是程序员，wiki 是代码库。）

> You rarely ever write or edit the wiki manually — it is the domain of the LLM.
> （你几乎从不手工写或改 wiki——那是 LLM 的地盘。）

## 两个特殊文件：index.md 和 log.md

Karpathy 把"索引"拆成了两个分工明确文件：

- **`index.md` —— 面向内容的目录**（管空间）：按类别列出每个页面、链接与一行摘要。提问时 LLM 先读它定位，再往下钻。**每次摄取后更新。**
- **`log.md` —— 面向时间的记录**（管时间）：追加式流水账，记录何时摄取、何时提问、何时体检。一个技巧是每条记录用一致前缀开头，例如 `## [2026-04-02] ingest | Article Title`，这样就可以用简单的 unix 工具解析：

```
grep "^## \[" log.md | tail -5
```

一句话对照：`index.md` 回答"**这里都有什么**"，`log.md` 回答"**最近发生了什么**"。

## 三个核心操作

1. **Ingest（摄取）**：LLM 读完整份来源 → 提炼要点 → **更新 10–15 个既有 wiki 页面** → 若引入新实体/概念则新建页面 → 更新索引 → 在日志里追一条记录。一份来源会牵动多个页面，把新信息织进已有知识结构。
2. **Query（提问）**：LLM 检索相关页面 → 综合作答（带回链引用）→ **把有价值的产出回存进 wiki 成为新页面**。这是关键洞察：传统聊天里发现会消失在对话历史中，这里每个有价值的回答都被收进知识库，知识**复利**而非蒸发。
3. **Lint（体检）**：定期扫描全库，查找——页面之间的矛盾、被新来源取代的过时声明、没有入链的孤儿页、被提及却缺少独立页面的重要概念、缺失的交叉引用、可通过搜索填补的数据空白。

## 规模与边界（务必连着前提记）

Karpathy 说自己在一个研究主题上积累了**约 100 篇文章、40 万字**，且**没有直接写过一个字**。他还提到：在这个规模下，不一定需要很复杂的 RAG 基础设施。

**但这句话有前提**：成立的原因不是模型不需要检索了，而是他先把资料整理成了更有结构的知识层——查询时先读 `index.md`，再看摘要、概念页、相关页，路径比直接翻原始资料短得多。所以结论有边界：

- 主题相对聚焦、规模未膨胀时：`index + summaries + concept pages` 确实可能替掉一部分复杂检索。
- 数据量继续上去、知识域越来越杂、或要求强可追溯性时：大概率仍需与更正式的检索、引用、校验机制配合。

Karpathy 本人留了明确的边界线：

> **human owns verification**（验证的责任在人）。

## 已知瓶颈（来自社区讨论）

1. **查询瓶颈**：wiki 页面超过几百页后，grep 会变慢。"我上周添加了关于 X 的哪些内容？""显示所有标记为未验证的内容"这类查询，靠简单读文件无法实现。索引在初期很有帮助，但无法扩展。
2. **结构瓶颈**：无论你是否计划，结构都会悄然形成——前言、命名规范、文件夹规则。到某个时刻你会意识到，自己是在与工具对抗，而不是与它协同。
3. 社区给出的应对方向：
   - **Binder**（`github.com/mpazik/binder`）：与其让文件慢慢演变成数据库，不如从结构化数据入手，渲染成 Markdown；数据进事务日志、在 SQLite 建索引，代理通过 API 双向读写。
   - **Knowledge Engine**（`github.com/tashisleepy/knowledge-engine`）：双层检索，wiki 层兼容 Obsidian 供人读，Memvid 层（`.mv2` 单文件内存）供机器查询，搜索 < 5 毫秒，桥接器以原子方式保持两层同步。

## 它不只是一套知识库方案，也是一种"分发方式"

Karpathy 特意解释为什么把这事写成 gist：在 LLM agent 时代，**不一定非要先分享一个完整 app 或一份完整代码**，也可以先把思路写成一个相对抽象的 **idea file**，再交给对方的 Agent 去结合自己的场景落地。

所以 `llm-wiki.md` 写得很克制——没有把目录结构、字段、模板、工具链一次性写死，而是有意留出空间。这解释了我们为什么可以在它的骨架上，长出自己的一套 wiki。

## 社区实践经验（摘要）

- **先分类，再提取**：报告 / 信件 / 会议记录应该走不同的处理流程，不要一刀切。
- **给索引设一个 token 预算**：读 `index.md` 时控制篇幅，不要每次都把全文拉进来。
- **每种实体类型一个模板**：人物页和事件页需要不同字段，不要只用一个通用模板。
- **一次 ingest 一份来源，并且人参与**：Karpathy 自己偏好一次只喂一份，边看摘要边决定要强调什么——**不是完全无人值守的一键流水线**。
- **下一步方向（Karpathy 仍在探索）**：随着 wiki 规模增长，可用合成数据做微调，让 LLM 把知识"记进权重"，而不只是放在上下文窗口里。
