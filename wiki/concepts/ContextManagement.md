# ContextManagement（上下文管理）

## 定义

**上下文管理 = 当内容逼近或超出 [[Context|上下文窗口]] 时，主动对窗口里的内容做增删改，让长任务还能继续做下去。**

它回答的是 [[Context]] 留下来没答的那个问题：窗口满了，**只能**眼睁睁看着最早的内容被截断吗？

不是。截断只是"什么都不做"时的默认结果；工程上有更主动的做法。

## 核心机制：四种思路

| 思路 | 做什么 | 代价 |
|---|---|---|
| 截断 truncate | 什么都不做，最早的内容被挤出去 | 丢失早期信息，而且是"无声地丢" |
| 编辑 context editing | 主动删掉已用完的工具结果、冗余的历史片段 | 需要判断"哪段已经没用了"，判断错就丢错 |
| 压缩 / 摘要 compaction | 把长段落改写或概括成更短的版本，保留要点 | 摘要必然有损；概括角度选错，会丢掉后文需要的信息 |
| 外置 memory / retrieval | 把内容存到窗口之外，需要时再取回 | 多一套存取机制；取回时要再花 token 放回来 |

这几种不是互斥的选项，实际系统通常**组合使用**。

## 与"省着用"的分工

这里容易和 [[ProgressiveDisclosure]] 混——两者都在对付上下文有限，但**动作方向不同**：

| 对比项 | [[ProgressiveDisclosure]] | 上下文管理 |
|---|---|---|
| 时机 | 内容**还没进**窗口 | 内容**已经在**窗口里 |
| 动作 | 按需分层加载，不该读的先不读 | 编辑 / 压缩 / 挪出去 |
| 目标 | 别让它占地方 | 占满了之后腾地方 |

一句话：**渐进式披露是"别乱吃"，上下文管理是"吃多了怎么消化"。**

## 为什么重要

[[Agent]] 的循环是"观察 → 决定 → 行动 → 把结果放回上下文"，这会**持续往窗口里累积内容**：工具返回的大段日志、每一轮的推理过程，越跑越多。不管理，Agent 就是跑得越久越健忘。

所以上下文管理与 [[Memory]] 是同一枚硬币的两面：**一个管怎么把内容挪出去，一个管怎么把内容取回来。** 而两者的物理边界，都是 [[Token]] 的额度。

## 使用边界

- **压缩必然有信息损失**：摘要一旦生成，被略去的细节就真的没了。所以压缩要以"下游还需不需要"为准，不能只看"能不能变短"。
- **编辑需要判断力**：判断"这段还有没有用"一旦出错，误差会沿多步任务一路放大（与 [[Memory]] 的取回风险同源）。
- **外置不是免费的**：存出去的内容还要能被取回来，否则等于删了。存取机制本身需要设计。
- **不是所有任务都值得**：单轮问答根本撞不到窗口上限；只有**长任务 / 多步 Agent** 才需要这套办法。
