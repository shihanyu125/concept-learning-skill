# Memory（记忆）

## 定义

**记忆是让 AI 跨步骤、跨会话保持状态连贯的能力**，是 [[Agent]] 三项核心增强能力（检索 / 工具 / 记忆）之一。

原始资料的表述：记忆 = "能记住对话过程和中间状态，跨步骤保持连贯"。（来源：[[agent]]）

## 核心机制：为什么"记忆"需要专门设计

理解记忆的钥匙是一句反直觉的话：**大语言模型本身是无状态的。**

它不像人有连续的意识流。每一次请求，它都是**从头把当前上下文看一遍**，然后给出回答——上一次请求里发生过什么，它并"不知道"，除非那些内容又被放进了这一次的上下文里。

这带来一个关键推论：

> **所谓"AI 记住了"，本质上都是"该记的东西恰好又回到了上下文里"。**

所以"记忆能力"在工程上要拆成三件事才站得住：

| 环节 | 做什么 | 风险点 |
|---|---|---|
| **写入** | 决定什么值得被记下来 | 记太多 → 噪音；记太少 → 健忘 |
| **存储** | 把它放到上下文窗口之外的持久位置 | 存得散 → 取不回来 |
| **取回** | 在合适的时候把它重新放回上下文 | 取错 → 答非所问；取全 → 挤爆窗口 |

这个拆法解释了两个常见困惑：

1. **为什么"AI 忘了"不是 bug，而是默认状态**——忘才是默认，记住需要专门设计。
2. **为什么"能记住偏好"这类宣传，往往不是"它真的记得"，而是"它在每次对话时把一份画像重新塞回了上下文"**。

## 记忆分三层（存储环节的实际分工）

上面这个"存储"环节，实践中不是一坨，而是**按作用范围分三层**（来源：[[]]）：

| 层级 | 存在哪里 | 作用范围 | 谁来写 |
|---|---|---|---|
| **云端记忆** | 服务端 | 跨设备、跨会话 | 系统**自动**学习（用户画像）+ 按需检索历史对话 |
| **用户级本地记忆** | `~/.workbuddy/MEMORY.md` | 当前用户的**所有项目** | 用户明确要求时，AI 写入 |
| **工作区记忆** | `<项目>/.workbuddy/memory/` | **仅当前项目** | AI 完成实质工作后写入 |

分层的意义在于**范围匹配**：一个只对某个项目成立的约定，不该污染你在所有项目里的行为；反过来，一条跨项目的个人偏好，也不该在每个仓库里各抄一遍。见 [[WorkBuddy]]。

### 工作区记忆内部还要再分两个文件

| 文件 | 记什么 | 写入方式 |
|---|---|---|
| `YYYY-MM-DD.md` | **每日工作日志**：今天干了什么 | **只追加（append-only）**，永不覆盖 |
| `MEMORY.md` | **长期项目笔记**：这个项目的规矩是什么 | 按主题整理，有字数上限 |

**为什么必须分？** 因为"**时间线**"和"**结论**"是两种东西：

- 日志要**保真**——按时间堆着，不回头改，所以能当证据；
- 结论要**精炼**——会被反复修订、覆盖、合并，所以不能当证据。

混在一个文件里，两边都会变差：要么日志被改写而失去可信度，要么结论被淹没在流水账里找不着。

> 这套思路在本仓库还有个同构的例子：wiki 的 `log.md` 同样是**只追加**（管时间），而 `index.md` / `overview.md` 是**随时被修订**的（管空间与结论）。区别只是 wiki 记"知识"，memory 记"工作"。

## 什么该记，什么不该记

**该记**：

- 有长期价值的结论、决定、约定（"这个项目用 3.12 版本 Python，不用最新"）
- 踩过的坑与规避方法
- 用户明确表达的偏好（"诊断类任务先只看不动"）

**不该记**：

- 一次性的搜索结果、临时路径
- 工具报错的过程（除非它引出了可复用的教训）
- **能从文件本身读出来的内容**——重复记录 = 制造不一致的风险

**判断口诀**：**如果这件事只有这一次有意义，别记；如果下次还会用到，记。**

这条口诀和 [[LLMWiki]] 里"一次性问答不值得建页"是同一条原则在不同对象上的应用：**判断标准是"复现频率"，不是"当下重要性"。**

## 记忆 ≠ 技能

这两个经常被混为一谈，其实是两种东西（来源：[[]]）：

| | 记忆（Memory） | 技能（[[Skill]]） |
|---|---|---|
| 回答的问题 | **你是谁、你的项目是什么规矩** | **这类任务该怎么做** |
| 本质 | **信息** | **流程** |
| 复用范围 | 随项目变化 | 可跨项目复用 |

同一份经验，写进记忆还是做成技能，看它更偏"**事实**"还是更偏"**步骤**"：

- 「这个项目 Python 用 3.12」→ 记忆
- 「怎么在 macOS 上装 Python 3.12 的完整步骤」→ 技能

## 与上下文的关系：记忆的物理上限

记忆不是无限的，因为"取回"这一步要占用 [[Context]]：

- 上下文窗口有硬上限，超出即被截断；
- 塞进去的历史越多，留给当前任务的余地越小；
- 窗口内的信息被平等对待，**不会自动"知道哪条重要"**。

推论：**记忆能力的强弱，很大程度上取决于"能不能只把最该记的那一点点取回来"，而不是"能存多少"。** 这也是 [[ProgressiveDisclosure]] 的思路——按需分层，而不是一次全灌。

## 与 Agent 的关系

[[Agent]] 靠"观察 → 决定 → 行动 → 把结果放回上下文"的循环推进任务。这个循环能持续下去，前提就是记忆：

- **没有记忆**：每一步都从零开始，无法完成需要多步累积的任务；
- **有记忆**：中间状态被保留，Agent 才谈得上"自己规划、自己调工具"。

反过来说，[[Workflow]] 通常不依赖模型的记忆——流程由代码保存和传递状态，这也是它更稳定、更好排查的原因之一。

同一个"无状态"前提，在 [[Automation]] 那里还有一个直接后果：**到点执行时会话早已结束，所以自动化的 `prompt` 必须自包含**——那是唯一能带过去的传递通道。

## 易混淆的点

- **记忆 ≠ 上下文。** 上下文是"这一次能看到的东西"，记忆是"跨多次保持连贯的能力"。记忆必须借上下文才能生效，但两者不是一回事。
- **记忆 ≠ 参数里的知识。** 模型权重里的是训练得来的"常识"，不会因为你今天说了什么而改变；会变的、需要存的是工作记忆。
- **"记性好"不等于"更聪明"。** 记错的东西比不记更糟——取回环节的错误会被后续步骤一路放大。
