# 无状态

## 一句话

无状态指的是：一个系统**不保留上一次调用留下的任何痕迹**——你每次找它，它都像第一次见你；所有"它记得我"的效果，都是外部把信息重新喂进去造出来的。

## 核心机制

### 无状态系统的行为特征

- **单次推理**：收到输入，算出输出，结束。中间不写任何持久化状态；
- **不区分调用者**：同一个请求发给它一万次，得到一万次同样的回答；
- **跨次调用无关联**：上一次说了什么，与这一次毫无关系。

在无状态系统里，**"记忆"不是系统的属性，而是调用方的责任**。想要连续对话，就得每次把历史一起发过去。

### 为什么设计成无状态

从工程与安全角度看，无状态有三个硬好处：

| 好处 | 说明 |
| --- | --- |
| **可水平扩展** | 没有状态要同步，加机器就能加容量，请求随便丢给哪台都行 |
| **不会被拖垮** | 状态意味着要为每个调用者保留资源；能被无限累积的状态，就是可以被低成本耗尽的资源 |
| **故障可恢复** | 任意一台实例挂掉都不丢东西，因为本来就没存东西 |

这也解释了一个常见疑问：**为什么不能让模型自己记住我？** 让服务端为每个用户累积上下文，等于把"持续占用资源"的开关交到用户手上。所以状态必须挪到调用方一侧——由用户自己存、自己发、自己管。

### 有状态与无状态的对照

| | 无状态 | 有状态 |
| --- | --- | --- |
| 是否记得上一次 | 不记得 | 记得 |
| 状态存在哪 | 调用方（客户端） | 服务方（服务端） |
| 扩容难度 | 容易 | 难，要处理状态同步 |
| 代价 | 每次要重复发送上下文 | 服务方要持续占用资源 |

### 同一个原理的其他面孔

- **计算环境**：交互式运行环境里的变量只活在会话内，重启运行时环境，之前定义的变量全部消失——因为它同样是无状态的，内存里的东西没有落盘；
- **上下文窗口**：既然系统不记，那就只能每次把必要信息塞进有限的窗口里，于是"窗口是稀缺资源"这条约束就成立了；
- **记忆系统**：记忆系统的全部工作，就是给一个无状态的核心补上一个外部的、可重取的容器。

## 生活类比

**每天都会失忆的天才实习生。** 他智商极高、干活极快，但每天早上一进门就完全不记得昨天的事。你要做的不是"教他记住"，而是**每天早上把「我是谁、我们在做什么、上次做到哪了」重新讲一遍**——讲得越清楚，他干得越好。

"重新讲一遍"就是注入上下文，"讲什么、讲多少"就是记忆系统要解决的问题。

## 常见误解

- **误解一：模型在"记住"我。** 实际是客户端每次把历史重发了；关掉这个机制，它立刻失忆。
- **误解二：写成文件的东西会被自动记住。** 文件只是被存下来了，**没被读进上下文的内容等于不存在**。
- **误解三：无状态就是弱。** 恰恰相反，正因为无状态才撑得住规模；把状态外置是一种刻意选择，不是缺陷。
