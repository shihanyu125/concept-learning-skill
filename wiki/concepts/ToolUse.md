# ToolUse（工具调用）

## 定义

**工具调用是让模型从"只会说"变成"真能动手"的那座桥。**

模型本身只能生成文本——它能"告诉你怎么订机票"，但订不了。工具调用就是：模型输出一个结构化的"请求调用某工具"的意图，由外部程序真正去执行（搜网页、跑代码、查数据库、发邮件），再把执行结果交回给模型，让它据此继续。

原始资料的表述：[[Agent]] 三项核心增强能力之一的"工具"，指"能调用外部工具——搜网页、跑代码、查数据库、发邮件等"。（来源：[[agent]]）

## 核心机制

一轮工具调用的循环：

```
模型判断"我需要用到 X 工具" → 输出调用请求（工具名 + 参数）
        ↓
外部程序执行 → 拿到真实结果（或报错）
        ↓
结果被放回上下文 → 模型看到结果，决定下一步
```

三个要点：

1. **模型自己不做事，它只"发指令"。** 真正的动作由外部程序执行。所以工具的安全性、权限、边界，全部由调用方控制。
2. **工具的结果必须回到上下文里才有用。** 这一点把工具调用和 [[Memory]] 绑在了一起：每一轮的结果都要占 [[Context]]，工具用得越多，窗口消耗越快。这也是长链路 Agent 容易"跑着跑着就忘事"的原因之一。
3. **工具要有清晰的描述。** 模型靠工具的名称与说明来判断"什么时候该用它"——描述含糊，模型就会在错误的时机调用、或该调时不调。

## 最容易搞错的一点：会调工具 ≠ 是 Agent

这是 [[Workflow]] 与 [[Agent]] 那条界线最常被误判的地方：

- **很多自动化脚本也调工具**（调 API、读文件、发通知），但**下一步调什么由代码预先写死** → 那是 [[Workflow]]。
- 只有当**"下一步调不调、调哪个"由模型自己动态决定**时，才构成 Agent 意义上的工具调用。

所以「用了工具」不能作为判据；**"下一步由谁决定"才是判据**。

## 为什么工具是 Agent 能力的关键一环

三项增强能力里，工具是最直接体现"动手"的一项：

| 能力 | 让模型获得什么 |
|---|---|
| 检索 | 看得更多（外部知识） |
| **工具** | **做得到（真实动作）** |
| [[Memory]] | 记得住（跨步骤连贯） |

只有"看"和"记"而没有"做"，[[Agent]] 仍然只能给出建议；有了工具，它才可能真正把事情办完——代价是**它能造成的后果也变成了真实的**。

## 使用边界与风险

- **副作用是真实的。** 读操作（搜索、查询）出错代价小；写操作（发邮件、下单、删文件）出错就收不回来。这是工具调用与纯文本生成最本质的差别。
- **需要授权与确认。** 涉及不可逆动作时，应当由人确认后再执行——把"能自动做"和"该自动做"分开。
- **错误会沿链路放大。** 一次工具返回的错误结果若没被发现，会被后续步骤当成事实继续使用。
- **不是工具越多越好。** 工具过多会让模型在"该用哪个"上犯错，也会挤占上下文。

## 关联

- [[Agent]] — 工具是它的三项核心增强之一；"会调工具"本身不构成 Agent
- [[Workflow]] — 对照面：它也调工具，但流程写死
